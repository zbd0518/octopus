# 分组编辑器成员状态展示 Brainstorm

> Stage 0 | 2026-07-24 | 下一步：cs-feat（由主入口选择 lane）

## 想做什么、为什么

新增/编辑路由分组时，左侧候选与右侧已选渠道模型缺少「能不能进组」的静态风险信号。  
昨天已做「渠道已禁用」过滤与右侧徽章，但仍缺：无可用 Key、上游健康风险的可读标签，且左侧模型行几乎裸奔。  
目标是保存前一眼看出硬风险与健康风险，避免把坏成员塞进分组；不发测活请求。

## 考虑过的方向

### 方向 A：轻量静态态

- 描述：复用已有 `enabled` / `upstream_metrics` / `useChannelList.keys`，左右统一风险徽章与汇总
- 价值：零探测成本、实现局部、与昨天 filter feature 同层
- 代价：不是实时可用，无 metrics 时静默
- 结论：**选定**

### 方向 B：编辑器内测活

- 描述：复用详情测活 + `test-draft`
- 结论：否决（本轮）；成本高，与「轻量」目标不符

### 方向 C：进入编辑器自动 probe

- 结论：否决；打扰与成本最大

## 已敲定的设计点

1. **范围**：仅分组 Editor UX；左右两侧都展示。**已确认**
2. **信号 1 渠道已禁用**：`LLMChannel.enabled === false`；渠道头 + 模型行 + 右侧徽章/汇总。**已确认**
3. **信号 2 上游健康风险**：基于 `upstream_metrics.success_rate`；阈值复用 StatusBars（≥0.9 安静；0.7–0.9 amber；&lt;0.7 且 &gt;0 red）；文案用「健康一般 / 成功率低」，**禁止**「可用/不可用」以免与测活语义撞车；无数据不展示。**已确认**
4. **信号 3 无可用 Key**：渠道 `keys` 中无 `enabled && channel_key 非空` 即为硬风险；与禁用同级（醒目徽章 + 进汇总）；数据用编辑器已有 `useChannelList` 前端 join，不改后端。**已确认**
5. **不做**：自动测活、禁止添加、保存自动剔除、改运行时路由、无 metrics 当故障。**已确认**
6. **右侧汇总**：扩展为禁用数 / 无 Key 数 / 健康风险数（有才显示）。**已确认**

## 选定方向与遗留问题

选定方向 A：分组编辑器静态风险可视化。  
核心行为：左右同口径展示三类信号；硬风险（禁用、无 Key）醒目；健康风险标签化。  
明显不做：测活与运行时变更。  
最大未知：无（实现层阈值与 join 口径已定）。  
遗留给实现：i18n keys；纯函数抽取（类似 `editor-filters`）便于单测。
