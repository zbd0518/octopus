# 渠道详情展示所属路由分组 Brainstorm

> Stage 0 | 2026-07-24 | 下一步：cs-feat（由主入口选择 lane）

## 想做什么、为什么

渠道侧只能看配置与指标，无法反向知道「这个渠道被哪些**路由分组**用到了」。  
运维同时有三类动机：日常打开详情顺带知道被谁用、对账是否进了如 `gpt-5.6` 之类的组、禁用/改 Key/删除前判断影响面。  
分组侧已有成员编辑、删除渠道会 purge `GroupItem`，但渠道详情仍是引用关系盲区。  
真问题是：**在渠道详情补齐「被哪些路由组引用」的只读反向视图，并支持跳到分组继续改**。

注意：路由 `Group`（`channel_id + model_name` 成员）≠ 渠道文件夹 `ChannelGroup`；本能力只做前者。

## 考虑过的方向

### 方向 A：只展示分组名 badge

- 描述：详情加一排「已加入：xxx」
- 价值：实现最轻，日常浏览够用
- 代价：不知进了哪些模型；审计只能猜影响面
- 结论：否决（对账与审计欠账）

### 方向 B：分组 + 本渠道在组内的模型

- 描述：按路由分组聚合展示组名与本渠道贡献的模型；0 组时空态
- 价值：浏览 / 对账 / 改前审计信息充分
- 代价：UI 略重；需按 `channel_id` join 分组 items
- 结论：基础形态，选定

### 方向 C：可操作反向入口（详情内改组成员 / 完整向导）

- 描述：B + 在详情增删成员或完整加组向导
- 价值：配置闭环更短
- 代价：与分组编辑器职责重叠，范围膨胀
- 结论：否决（第一期）

### 方向 B+：B + 组名跳转分组编辑（选定）

- 描述：在 B 上组名可点打开对应分组编辑器；详情内不改成员
- 价值：审计可继续改配置，成本可控
- 代价：需接既有跳转/深链
- 结论：**选定**

## 已敲定的设计点

1. **范围**：仅渠道详情**查看态**独立 section「所属路由分组」。**已确认**
2. **展示粒度**：按路由分组聚合——**组名 + 本渠道在该组的 `model_name` 列表**；同一渠道多模型多组要正确聚合。**已确认**
3. **空态**：未加入任何路由分组时明确文案，不静默空白。**已确认**
4. **交互**：组名可点 → 打开对应**分组编辑器**；详情内**不增删** `GroupItem`。**已确认**
5. **语义边界**：只展示路由 `Group`，不与 `ChannelGroup` 文件夹混区。**已确认**
6. **数据**：优先复用已有分组列表，前端按 `channel_id` 过滤 join；第一期不硬上专用 API，量大再考虑。**已确认**
7. **不做**：详情内改组成员、空态完整向导、专用测活/健康分、与 ChannelGroup 混排。**已确认**

## 选定方向与遗留问题

选定方向 B+：渠道详情只读反向关系 + 组名跳转编辑。  
核心行为：打开详情即见所属路由组及贡献模型，可点组名进编辑器。  
明显不做：详情写组成员、专用探测、ChannelGroup 混排。  
最大未知：现有前端是否已有「打开指定分组编辑器」的 jump / 深链可复用（实现时核对 `stores/jump` 与 group 模块）。  
遗留给实现：i18n keys；join 纯函数可单测；跳转失败时降级为只展示不报死。
